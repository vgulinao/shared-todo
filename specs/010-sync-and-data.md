# 010 — Sync protocol and data model

The core of the assignment. Everything here is our own design; no sync library is involved.

## Goals

1. Two people editing the same list see each other's changes within a round trip.
2. The user's own change appears instantly, before the server confirms it.
3. A client that reconnects ends up with the server's state plus its own unconfirmed changes.
4. Every operation can be applied twice without harm, so retries and replays are safe.
5. Small enough to explain in five minutes.

## Data model

```sql
lists (
  id          TEXT PRIMARY KEY,   -- uuid
  title       TEXT NOT NULL,
  edit_token  TEXT NOT NULL UNIQUE,
  view_token  TEXT NOT NULL UNIQUE
)

items (
  id          TEXT PRIMARY KEY,   -- uuid, generated by the client
  list_id     TEXT NOT NULL REFERENCES lists(id) ON DELETE CASCADE,
  parent_id   TEXT REFERENCES items(id) ON DELETE CASCADE,  -- null for top-level items
  title       TEXT NOT NULL,
  description TEXT,               -- markdown, S9
  done        INTEGER NOT NULL DEFAULT 0,
  cost        REAL,               -- S8
  position    REAL NOT NULL       -- ordering among siblings, S6
)
```

Columns for later stories are in the schema from the start so no migration is needed during the
assignment. Sub-tasks are one level deep: a sub-task cannot have children.

## Identity and permissions

- No accounts. Each browser generates a `clientId` (uuid) once and keeps it in `localStorage`.
  It only labels operations; it grants nothing.
- Access is by token in the URL: `/l/<token>`. The server resolves the token to a list and a role:
  `edit` if it matches `edit_token`, `view` if it matches `view_token`, otherwise 404.
- The server rejects write operations on a `view` connection. The client also hides editing
  controls, but the server check is the one that matters.
- Tokens are 128-bit random, URL-safe. Knowing the view token does not reveal the edit token.

## Transport

- `POST /api/lists` `{ title? }` → `201 { editToken, viewToken }`. The only REST endpoint.
- `GET /ws?token=<token>` upgrades to a WebSocket. Messages are JSON, one object per frame.

## Messages

Server → client

```ts
{ type: "snapshot"; list: { id: string; title: string; role: "edit" | "view" }; items: Item[] }
{ type: "op"; op: Op }                 // an operation the server has applied (any client's)
{ type: "rejected"; opId: string; reason: string }
```

Client → server

```ts
{
  type: "op";
  op: Op;
}
```

## Operations

Every op carries `opId` (uuid, generated by the client) and `clientId`.

```ts
type Op =
  | { kind: "createItem"; item: Item } // whole item, id chosen by client
  | {
      kind: "updateItem";
      id: string;
      patch: Partial<Pick<Item, "title" | "description" | "done" | "cost">>;
    }
  | { kind: "moveItem"; id: string; parentId: string | null; position: number }
  | { kind: "deleteItem"; id: string } // also deletes its sub-tasks
  | { kind: "renameList"; title: string };
```

Idempotency is by construction, not by bookkeeping:

| op         | server SQL                           | applied twice     |
| ---------- | ------------------------------------ | ----------------- |
| createItem | `INSERT OR IGNORE`                   | second is a no-op |
| updateItem | `UPDATE ... WHERE id = ?`            | same result       |
| moveItem   | `UPDATE ... SET parent_id, position` | same result       |
| deleteItem | `DELETE ... WHERE id = ?` (cascade)  | second is a no-op |
| renameList | `UPDATE lists SET title`             | same result       |

An op that references a missing item (deleted by someone else meanwhile) is a no-op on both sides.

## Client algorithm

State: `items: Map<id, Item>`, `pending: Map<opId, Op>`, `status: "connecting" | "online" | "offline"`.

1. **User acts** → build op → `apply(items, op)` locally → add to `pending` → send if online.
2. **Receive `op`** → `apply(items, op)`. If `op.opId` is in `pending`, remove it (this is the ack).
   Ops from other clients are applied the same way; there is no special case.
3. **Receive `snapshot`** → replace `items` with the snapshot, then re-apply every op still in
   `pending` in insertion order, then resend them. This is the whole reconnect story.
4. **Receive `rejected`** → remove from `pending`, show a brief error, and rely on the next
   snapshot or op stream to correct local state (in practice only happens for `view` role).
5. **Socket closes** → `status = "offline"`, reconnect with exponential backoff (0.5 s → 10 s).

`apply` is a pure function in `shared/` with tests. The same function runs on every client, so all
clients that have seen the same ops in the same order hold the same state.

## Server algorithm

1. On upgrade: resolve token → list + role, or close with 4004. Send `snapshot`. Add socket to the
   room for that list.
2. On `op` from a `view` socket → send `rejected`, do nothing else.
3. On `op` from an `edit` socket → validate shape → run the SQL → broadcast `{type:"op", op}` to
   every socket in the room, sender included. The sender treats its own op coming back as the ack.
4. On close: remove from the room.

The server does not keep list state in memory. SQLite is the state; the room is just sockets.

## Conflict rules

- Ops are applied in the order the server receives them. Last write wins per op.
- Two people editing different fields of the same item both keep their change, because
  `updateItem` patches only the fields it carries.
- Two people editing the same field at the same time: the later arrival wins, the earlier one sees
  their text replaced within a round trip. Acceptable for a shopping list; documented in the README.
- `deleteItem` wins over a concurrent `updateItem` (the update finds no row).
- Concurrent `moveItem` on different items converge because each sets an absolute position.
  Concurrent moves of the same item: later arrival wins.

## Ordering (S6)

`position` is a float. New items get `max(position) + 1` among their siblings. A move sets
`position` to the midpoint between the new neighbours, or `min - 1` / `max + 1` at the ends.
Doubles allow roughly 50 consecutive midpoint insertions at the same spot before precision runs out;
if `newPosition` equals a neighbour, the client renumbers the siblings to integers first. Not expected
to trigger in normal use, tested anyway.

## Offline (S10, stretch)

Everything above already makes this mostly work: while `offline`, user actions still `apply` locally
and accumulate in `pending`; on reconnect the snapshot + replay step sends them. The additional work
is only to persist `pending` and the last known `items` in `localStorage`, so a page reload while
offline does not lose them. If S10 is cut, nothing in this document changes.

## What we deliberately did not build

- **Version numbers and an op log** for delta sync. A snapshot of a to-do list is a few KB; sending
  it on every connect is simpler and fast enough. With large lists we would add a per-list version and
  send only ops since the client's last version.
- **Per-field timestamps** for smarter conflict resolution. Last write wins in server order is
  enough for the use case; the rule is one sentence and predictable.
- **Multi-instance support.** Rooms live in one process. Scaling out would need a pub/sub channel
  between instances (Redis or Postgres LISTEN/NOTIFY) and Postgres instead of SQLite.
